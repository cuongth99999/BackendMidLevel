# Magenest_EventRegistration

Section 6 — Developing with Adminhtml.

This module bundles two related admin features around an **Event** entity:

- **Exam 1 — Custom Form + Grid UI**: admin creates/edits *Events* through a sidebar-driven form page that also embeds an inline-editable "Default Schedule" grid auto-generated from the form fields.
- **Exam 2 — Message Queue mass action**: a "Register Event" mass action on the Customer grid opens a modal (event select → event-time select → note) and fans the chosen customers out to a `db`-backed message queue in **batches of 1000**.

---

## 1. Domain model

```
magenest_event              (event_id, name, days_before_event, event_date, sort_order)
└── magenest_event_schedule (event_id ─FK→, day_of_week, schedule_date, event_time, details_message, position)
                            ↑
magenest_event_registration ─FK→ schedule_id
   ├── customer_id ─FK→ customer_entity
   └── event_id    ─FK→ magenest_event
```

Number of `magenest_event_schedule` rows for an event **always equals** the event's `days_before_event` value; rows are recomputed every time the form is saved.

`magenest_event_registration` has a `UNIQUE (customer_id, schedule_id)` constraint so the queue consumer is idempotent (re-running a message updates `note`/`status` instead of failing).

## 2. Setup

```bash
# After cloning / pulling
php bin/magento module:enable Magenest_EventRegistration
php bin/magento setup:upgrade            # also runs the customer seed patch (~3000 rows)
php bin/magento setup:di:compile
php bin/magento cache:flush

# Static assets (skip in developer mode)
php bin/magento setup:static-content:deploy -f adminhtml
```

After `setup:upgrade`:

- 3000 customers `evt_NNNNN@magenest.example` (password `Password123!`) are inserted directly (idempotent — re-running the patch only tops up to the target count).
- Tables `magenest_event*` are created via declarative schema.

Start the consumer to drain queued mass-register batches:

```bash
php bin/magento queue:consumers:start magenest.event.register.consumer --max-messages=1000
```

Or rely on Magento's cron, which auto-launches consumers configured in `app/etc/env.php → cron_consumers_runner`.

## 4. The Exam 1 page layout — the bit worth reading

> *Goal:* A single admin page with a **left sidebar** listing all events (+ "Add New Event"), and a **right area** containing a UI form (`Event Details` fieldset) **plus an embedded grid** (`Default Schedule`). The grid rows are auto-generated by JS from the form's `days_before_event` and `event_date` fields and support inline edit on two columns.

This is unusual because UI form components don't naturally know how to share horizontal space with a sibling block. The trick is to wrap both inside a layout `<container>` and let CSS Grid do the placement.

### 4.1 Layout XML — `view/adminhtml/layout/eventregistration_event_edit.xml`

```xml
<page layout="admin-1column">
    <body>
        <referenceContainer name="content">
            <container name="eventregistration.workspace"
                       htmlTag="div"
                       htmlClass="eventregistration-workspace">

                <!-- Left: PHTML sidebar block (server-rendered) -->
                <block class="Magenest\EventRegistration\Block\Adminhtml\Event\Sidebar"
                       name="eventregistration.event.sidebar"
                       template="Magenest_EventRegistration::event/sidebar.phtml"/>

                <!-- Right: UI form component (KO + UI data provider) -->
                <uiComponent name="eventregistration_event_form"/>

            </container>
        </referenceContainer>
    </body>
</page>
```

Key points:

- The `<container htmlTag="div" htmlClass="eventregistration-workspace">` is what gives us a single DOM parent so CSS Grid (`grid-template-columns: 220px 1fr`) can place sidebar + form on one row.
- `<uiComponent>` can sit **next to** a `<block>` inside a layout container. The UI form's KO bootstrap will run independently — the layout only cares about producing the HTML wrapper.
- `admin-1column` is reused as the page layout. We don't need `admin-2columns-left` because the column structure is provided by our own container, not by the page layout.

### 4.2 CSS Grid — `view/adminhtml/web/css/module.css`

```css
.eventregistration-workspace {
    display: grid;
    grid-template-columns: 220px minmax(0, 1fr);
    align-items: flex-start;
    gap: 24px;
}
```

`minmax(0, 1fr)` is important: without the `0` floor, the form's intrinsic content width can push the grid wider than the container and the form ends up cramped to ~50% of available width. `minmax(0, 1fr)` lets the form column shrink properly and fill the rest of the row.

> Why CSS Grid, not Flex? Initial attempt used `flex` with selectors targeting `> form`, `> .entry-edit`, etc. — but UI form components render as a generic `<div data-bind="scope: ...">`, so no specific selector reliably matched. Grid sidesteps the issue by positioning the **second** track regardless of element type.

### 4.3 Sidebar block — `Block/Adminhtml/Event/Sidebar.php` + `event/sidebar.phtml`

The sidebar is a plain PHTML block that lists `magenest_event` rows ordered by `sort_order` then `entity_id`. It marks the current event (`?id=` query param) as active and provides the "+ Add New Event" link to `*/event/new`.

This block lives **outside** the UI form's KO tree, so it's fully server-rendered and doesn't need any UI component plumbing.

### 4.4 UI form with embedded grid — `ui_component/eventregistration_event_form.xml`

Two fieldsets in one form:

```xml
<fieldset name="event_details">
    <field name="name"              formElement="input"/>
    <field name="days_before_event" formElement="input"/>
    <field name="event_date"        formElement="date"/>
    <field name="sort_order"        formElement="input"/>
</fieldset>

<fieldset name="schedule_fieldset">
    <dynamicRows name="schedule"
                 component="Magenest_EventRegistration/js/form/dynamic-rows-schedule">
        <settings>
            <addButton>false</addButton>           <!-- rows are auto-generated -->
            <columnsHeader>true</columnsHeader>
            <deleteProperty>false</deleteProperty>
            <dataScope>schedule</dataScope>
            <imports>
                <link name="daysBefore">${ $.provider }:data.days_before_event</link>
                <link name="eventDate">${ $.provider }:data.event_date</link>
            </imports>
        </settings>
        <container name="record" component="Magento_Ui/js/dynamic-rows/record">
            <field name="position"        formElement="input"/>     <!-- hidden -->
            <field name="day_of_week"     formElement="input"/>     <!-- disabled, computed -->
            <field name="schedule_date"   formElement="input"/>     <!-- disabled, computed -->
            <field name="event_time"      formElement="input"/>     <!-- editable -->
            <field name="details_message" formElement="input"/>     <!-- editable -->
        </container>
    </dynamicRows>
</fieldset>
```

`<dynamicRows>` is Magento's official "grid inside a form" widget — it renders a tabular layout where each "row" is a record with its own dataScope namespace.

### 4.5 The auto-generation JS — `web/js/form/dynamic-rows-schedule.js`

The custom JS extends `Magento_Ui/js/dynamic-rows/dynamic-rows` and listens to two imports declared in the XML:

```js
defaults: {
    listens: {
        daysBefore: 'rebuildSchedule',
        eventDate:  'rebuildSchedule'
    }
}
```

`rebuildSchedule()`:

1. Parses `eventDate` via **moment.js** (Magento ships it as `lib/web/moment.js`) with a list of accepted formats (`YYYY-MM-DD`, `MM/DD/YYYY`, `DD/MM/YYYY`, …). Necessary because the admin UI's date picker emits the locale display format, not always ISO.
2. Builds N row objects (N = `daysBefore`) walking backward from `eventDate`:
   - `day_of_week`: e.g. `Tuesday`
   - `schedule_date`: ISO `YYYY-MM-DD`
   - `event_time`/`details_message`: **preserved** from existing records, matched by `position`, so the user's inline-edited values survive a regen.
3. Sets the observable and reloads the dynamicRows:
   ```js
   this.recordData(rows);
   this.reload();
   ```

### 4.6 Where dynamicRows data actually lives — a gotcha worth knowing

`Magento_Ui/js/dynamic-rows/dynamic-rows.js` line 144 links `recordData` to:

```js
recordData: '${ $.provider }:${ $.dataScope }.${ $.index }'
```

For our component (`name="schedule"`, `dataScope="schedule"`) under the form's root dataScope `data`, **records live at `data.schedule.schedule.<idx>` in the source** — note the doubled `schedule`. So:

- **DataProvider** (`Model/Event/DataProvider.php`) must return:
  ```php
  $eventData['schedule'] = ['schedule' => $rows];   // nested!
  ```
  Otherwise the records are at `data.schedule.[0,1,…]` and dynamicRows won't read them.
- **Save controller** reads back from `$_POST['schedule']['schedule']`, with a fallback to a flat shape for resilience.

If the form ever saves the right number of rows but blank `event_time`/`details_message`, that's the symptom of mismatched paths — user-typed values flow into one path while initial data lives at another.

### 4.7 Server-side fields you should NOT trust from POST

`day_of_week` and `schedule_date` are rendered as `<disabled>true</disabled>` fields in the form. Whether a disabled UI field is included in the POST is implementation-dependent and brittle. So `Controller/Adminhtml/Event/Save.php::saveSchedule()` ignores those values and **recomputes** them from the canonical `event_date` + `days_before_event` + `position`. The form is then free to use those cells purely for display.

### 4.8 setEntityId quirk

`Magento\Framework\Model\AbstractModel::setEntityId($entityId)` has **no parameter type and no return type**. Subclasses (our `Model/Event.php`, `Model/EventSchedule.php`, `Model/EventRegistration.php`) and the matching `Api/Data/*Interface.php` must keep `setEntityId($entityId)` untyped. Adding `int` or `: self` triggers an LSP fatal at autoload that masquerades as an HTTP 500 with no entry in `var/log/exception.log` — only `/var/log/nginx/magento.error` shows it.

## 5. Exam 2 — Mass action + Message Queue flow

```
┌──────────────────────────────────────────────────────────────────────┐
│  Customer Grid (customer_listing UI component, extended via merge)   │
│                                                                      │
│  Mass action ── Register Event ──► JS opens a Magento modal          │
│                                                                      │
│  Modal:                                                              │
│    GET  /eventregistration/register/eventoptions  → events list      │
│    GET  /eventregistration/register/eventtimes?event_id=X → schedules│
│    POST /eventregistration/register/massregister  ──► PHP controller │
│                                                                      │
│  Controller:                                                         │
│    1. Resolve customer IDs:                                          │
│         mode=include → use selected[]                                │
│         mode=exclude → query customer_entity − excluded[]            │
│         (honors current grid filters + fulltext search)              │
│    2. MassRegisterPublisher::publish() chunks into batches of 1000   │
│    3. publisher->publish('magenest.event.register', $request)        │
│                                                                      │
│  Queue (db connection, topic magenest.event.register):               │
│    MassRegisterConsumer::process(MassRegisterRequestInterface $req)  │
│      → bulk insertOnDuplicate into magenest_event_registration       │
└──────────────────────────────────────────────────────────────────────┘
```

### 5.1 Listing extension — `view/adminhtml/ui_component/customer_listing.xml`

Same filename as `Magento_Customer`'s file → Magento **merges** them. We add:

```xml
<listingToolbar name="listing_top">
    <massaction name="listing_massaction">
        <action name="magenest_register_event">
            <settings>
                <type>magenest_register_event</type>
                <label>Register Event</label>
                <callback>
                    <target>openModal</target>
                    <provider>customer_listing.customer_listing.eventregistration_mass_register</provider>
                </callback>
            </settings>
        </action>
    </massaction>
</listingToolbar>

<container name="eventregistration_mass_register"
           component="Magenest_EventRegistration/js/grid/mass-register-action">
    <argument name="data" xsi:type="array">
        <item name="config" xsi:type="array">
            <item name="eventsUrl"    xsi:type="url" path="eventregistration/register/eventoptions"/>
            <item name="schedulesUrl" xsi:type="url" path="eventregistration/register/eventtimes"/>
            <item name="submitUrl"    xsi:type="url" path="eventregistration/register/massregister"/>
        </item>
    </argument>
</container>
```

How the wiring works (per `Magento_Ui/js/grid/massactions.js`):

1. Mass action `<callback>` makes Magento resolve the registry path via `registry.async(provider)` and then call `target` on the resolved component with `(action, selections)` args.
2. The `<container component="…/mass-register-action">` registers a JS UI component at that exact registry path — so the callback can reach it.
3. The JS component's KO template (`web/template/grid/mass-register-modal.html`) is rendered into the listing's KO tree but kept hidden by CSS (`.magenest-event-register-modal__body { display: none }`) until the Magento `modal` widget wraps it (the override `.modal-popup .magenest-event-register-modal__body { display: block }` un-hides it inside the popup).

> Pitfall: the CSS must be loaded **on the customer listing page**, not just on event-edit pages, otherwise the `display:none` rule never runs and the modal body is visible inline at the bottom of the grid. The module ships `view/adminhtml/layout/default.xml` that injects `module.css` into every admin page for exactly this reason.

### 5.2 Selection serialization

The mass action callback receives `selections` of shape:

```js
{
    selected:    [int],     // explicitly checked rows
    excluded:    [int],     // explicitly unchecked rows when excludeMode=true
    excludeMode: bool,      // true when user clicked "Select All NNN records"
    params:      { filters, search, … }   // current grid state
}
```

We POST it as:

```
mode      = "include" | "exclude"   // explicit flag, do NOT rely on excludeMode in payload
selected  = [id, id, …]             // present in both modes (empty in exclude mode)
excluded  = [id, id, …]
filters   = { field: value }
search    = "fulltext"
event_id, schedule_id, note, form_key
```

> Pitfall: `jQuery.ajax({ traditional: true })` serializes arrays as `key=v1&key=v2` (no `[]` suffix) — PHP only keeps the **last** value. Without `traditional`, jQuery emits `key[]=v1&key[]=v2` and PHP parses it as an array. **Do not use `traditional: true`** for grid selections; the symptom is "I selected all 20 customers on this page, but only customer_id=20 went to the queue."

### 5.3 Queue files

| File | Purpose |
| --- | --- |
| `etc/communication.xml` | Declares topic `magenest.event.register` with request type `MassRegisterRequestInterface` |
| `etc/queue_topology.xml` | Binds topic to queue on exchange `magento-db` (connection `db`) |
| `etc/queue_publisher.xml` | Routes the topic through the `db` connection |
| `etc/queue_consumer.xml` | Registers `magenest.event.register.consumer` → `MassRegisterConsumer::process` |

The DTO interface MUST have full PHPDoc (`@param`, `@return`, including `int[]` for the customer-id array) — `Magento_Amqp`'s communication validator parses PHPDoc, not PHP type hints. Missing annotations break `setup:upgrade` with:

> Module 'Magento_Amqp': Request schema definition has service class with wrong annotated methods

### 5.4 Idempotent consumer

`MassRegisterConsumer::process` uses `insertOnDuplicate(…, ['note', 'status'])` against `magenest_event_registration`. The table's `UNIQUE (customer_id, schedule_id)` constraint means re-processing the same message updates the note instead of throwing. Safe to retry / replay.

### 5.5 Verification queries

```sql
SELECT COUNT(*) FROM customer_entity WHERE email LIKE 'evt_%@magenest.example';

SELECT event_id, schedule_id, COUNT(*) AS customers
FROM magenest_event_registration
GROUP BY event_id, schedule_id;

-- Pending messages waiting for the consumer
SELECT topic_name, status, COUNT(*)
FROM queue_message_status
GROUP BY topic_name, status;
```
